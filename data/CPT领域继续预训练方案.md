# CPT 领域继续预训练 —— 完整方案

> 面向华为消费者业务客服领域基座模型训练  
> CPT = Continual Pre-Training = 在基座模型上继续做领域预训练  
> **核心目标**：注入领域知识 + 重塑语义表征 + 匹配领域分布，为后续 SFT/RL 提供地基

---

## 一、先澄清认知：CPT 在整个训练链条中的角色

### 1.1 心智模型：雕塑流程，不是技能树

```
                    ┌─────────────────┐
                    │   通用基座模型    │  ← 一块有基本形状的大理石
                    │ (DeepSeek/Qwen等) │
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
                    │      CPT         │  ← 粗雕：把整块石头往领域方向
                    │  领域语料继续预训  │     大幅塑形。所有能力（知识、
                    │  数据量最大的一步   │     理解、推理、表达）在这个
                    │                   │     阶段一起生长，不分先后
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
                    │      SFT         │  ← 精雕：在 CPT 塑好的领域轮廓
                    │  标注数据微调     │     上，刻出清晰的行为边界和
                    │  数据量中等       │     输出格式
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
                    │       RL         │  ← 打磨：在 SFT 框定的行为空间
                    │  偏好数据校准     │     内，打磨决策边界的锐度
                    │  数据量最小       │
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
                    │   领域基座模型    │  ← 一块完整的、精美的雕塑
                    │    (交付物)      │     所有能力浑然一体
                    └─────────────────┘
```

**核心主张：**

1. **能力不是分模块训练的，是在同一套参数上逐层精化的。** 不存在"先训练反讽模块，再训练意图模块，最后组合上场"。
2. **CPT 是最大的杠杆。** 它不针对任何单一能力，但通过重塑整个表征空间，同时提升了所有领域相关能力的基础水平。
3. **SFT 和 RL 是"收束"而非"拓展"。** CPT 拓宽了模型在领域内的可能性空间，SFT 和 RL 收束这个空间指向最优行为。
4. **"奇招"（涌现能力）来自 CPT 拓宽的空间 + 基座模型的通用智力。** SFT/RL 做得过重会压制涌现。

### 1.2 CPT 能做什么、不能做什么

| CPT 能做的（独特价值） | CPT 不太能做的 |
|---|---|
| 注入领域事实知识（产品参数、政策条款） | 让模型学会特定输出格式（"请用三段式回复"） |
| 重塑语义表征（"反讽句"在隐空间靠近"投诉意图"） | 在两条冲突策略中选择最优方案（那需要 RL） |
| 让模型获得"领域直觉"（类似球感） | 让模型一致地遵循安全规范（需要 SFT + RL） |
| 匹配领域语言分布（口语化、非标准表达） | 给模型装"方向盘"——行为对齐 |

### 1.3 CPT vs SFT vs RL 分工总结

| 维度 | CPT | SFT | RL |
|---|---|---|---|
| 操作对象 | 模型的内部表征（"感知世界的方式"） | 模型的输出行为（"怎么回应"） | 模型的决策边界（"在模糊地带选哪个"） |
| 本质 | 改变语义空间的拓扑结构 | 给表征空间标注"好路径" | 在候选路径中教模型选最优 |
| 类比 | 让篮球运动员泡在球场三年→获得球感 | 教练教标准动作→把球感转化成有效得分 | 比赛录像逐帧复盘→校准临场判断 |
| 数据要求 | 海量无标注/弱标注语料 | 高质量标注样本（数千到数万条） | 偏好对比数据（数百到数千对） |
| 能注入新知识吗 | ✅ 能 | ❌ 不能（你的团队已验证） | ❌ 不能 |
| 能赋予领域直觉吗 | ✅ 能（独有贡献） | ❌ 不能 | ❌ 不能 |

## 三、Phase 1：数据工程（占 50% 精力）

### 3.1 数据源盘点

以华为消费者业务客服场景为例：

| 数据源 | 类型 | 预估量级 | 价值评级 | 对应能力 |
|---|---|---|---|---|
| 内部产品文档/手册 | 结构化/半结构 | 10-50万篇 | ★★★★★ 核心知识 | 产品知识、参数 |
| 客服聊天记录（脱敏） | 非结构化对话 | 100万-1000万条 | ★★★★★ 分布匹配 | 对话分布、语感 |
| 内部知识库/Wiki | 半结构化 | 1-10万篇 | ★★★★ 知识+表达 | FAQ、诊断树 |
| 历史工单数据 | 半结构化 | 10-100万条 | ★★★★ 故障-方案映射 | 推理链 |
| 社区/论坛内容 | 非结构化 | 10-100万条 | ★★★ 真实用户语言 | 非标准表达、新梗 |
| 内部培训材料 | 结构化 | 1000-1万篇 | ★★★ 专业知识 | 技能培训 |
| 政策法规 | 结构化 | 100-1000篇 | ★★★ 合规知识 | 三包法、消保法 |

### 3.2 数据清洗流水线

```
原始语料
  │
  ▼
┌─────────────────────┐
│ ① 格式统一           │  统一编码(UTF-8)、统一换行符、
│                     │  去除二进制/乱码、HTML标签清洗
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│ ② 隐私脱敏           │  正则+NER模型双重扫描：
│                     │  手机号→<PHONE>、身份证→<ID>、
│                     │  地址→<ADDR>、人名→<PERSON>
│                     │  ⚠️ 客服场景特别关注：
│                     │  IMEI/SN码、订单号、精确位置
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│ ③ 质量过滤           │  - 长度过滤：<10字符 or >8192字符→剔除
│                     │  - 语言检测：非中文占比>50%→剔除或标记
│                     │  - 重复率：单条内部重复度>30%→剔除
│                     │  - 乱码率：不可打印字符占比>5%→剔除
│                     │  - 模板化内容：纯系统自动回复→降权
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│ ④ 去重               │  多级去重策略：
│                     │  L1: 完全匹配去重(哈希)
│                     │  L2: 近似去重(MinHash LSH, Jaccard>0.9)
│                     │  L3: 语义去重(Embedding相似度>0.95)
│                     │  ⚠️ 客服场景注意：
│                     │  模板回复("亲，请稍等")要保留一定比例
│                     │  但不能让它们主导分布
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│ ⑤ 文档切分           │  按语义边界切分，不是粗暴截断：
│                     │  - 产品文档：按章节/标题切
│                     │  - 对话：保持完整上下文
│                     │  - 工单：保持"故障-诊断-方案"链条
│                     │  - 目标长度：512-2048 tokens/条
└─────────┬───────────┘
          ▼
      清洗后语料
```

**客服场景特有的清洗注意事项：**

| 注意事项 | 处理方式 | 原因 |
|---|---|---|
| 客服话术模板大量重复 | 保留一定比例但降权 | 否则模型输出会变机械套话 |
| 对话中间的空白/"还在吗" | 保留 | 这是真实的对话节奏信息 |
| 用户错别字/叠字 | 保留 | 反映真实用户语言特征 |
| 中英混杂（"我那个phone的screen碎了"） | 保留 | 真实用户表达方式 |
| 纯系统自动回复 | 降权或剔除 | 价值低且重复度高 |

### 3.3 数据配比设计

这是 CPT 策略中最关键的决策，需通过实验调优：

| 数据类别 | 建议占比 | 细分 | 作用 |
|---|---|---|---|
| 客服真实对话 | **35-45%** | 在线文本 ~60%，语音转写 ~40% | 分布匹配、领域语感 |
| 产品/知识文档 | **25-30%** | 产品参数~40%，故障方案~30%，政策流程~30% | 知识注入主体 |
| 社区/真实用户语言 | **15-20%** | 论坛帖子~60%，社媒评论~40% | 非标准表达、新梗来源 |
| 通用语料（防遗忘） | **10-15%** | 维基百科/书籍/通用对话 | 防止通用能力退化 |
| 内部工单/培训 | **5-10%** | 工单、培训案例 | 故障-方案映射 |

**配比原则：**

1. 对话占比最高——因为最终模型是要在对话中使用
2. 通用语料不能省——否则模型会遗忘通用能力（灾难性遗忘）
3. 初始配比是假设，最终配比由实验验证

### 3.4 数据质量自查表

在训练启动前，逐项确认：

| 指标 | 含义 | 目标值 | 检测方法 |
|---|---|---|---|
| 文档级重复率 | 完全/近似重复占比 | <5% | MinHash LSH |
| Ngram重复率 | 高频ngram集中度 | 前100个ngram占比<3% | ngram频次分布 |
| 语言纯度 | 目标语言占比 | >95% | fastText/langdetect |
| 平均文档长度 | 单条语料平均token数 | 512-2048 | 分词后统计 |
| 领域词覆盖率 | 领域词在语料中出现率 | >90%的领域词至少出现N次 | 领域词典+频次统计 |
| 隐私泄露检查 | 是否残留PII | 0漏检 | 正则+NER扫描 |

## 四、Phase 2：训练策略设计

### 4.1 分词器评估

**如果基座模型的分词器对领域词不友好，CPT 效率大打折扣。**

```
检测方法：

  取1000个领域高频词（如"鸿蒙"、"昆仑玻璃"、"Pura"、"星闪"、"天生会画"）
  → 用基座分词器分词
  → 统计：
    ├─ 被分成1个token的占比  → 越高越好（理想>80%）
    ├─ 被分成2-3个token的占比 → 可接受
    └─ 被分成>5个token的占比  → 需要关注

  具体例子：
    "昆仑玻璃" → 看分词结果
      好的结果：["昆仑玻璃"] 或 ["昆仑", "玻璃"]  → ≤2 token
      坏的结果：["昆", "仑", "玻", "璃"]  → 4 token，逐字编码
    
    "Mate 60 Pro" → 看分词结果
      好的结果：["Mate", "60", "Pro"]
      坏的结果：["M", "ate", "60", "Pro"]

决策：
  - 如果>5 token/词的比例 <15%：不扩充词表，直接 CPT 硬训
  - 如果>5 token/词的比例 >30%：考虑扩充词表 + embedding 重新训练
  - 其他情况：优先直接训，标注为待观察项
```

### 4.2 训练超参数

| 关键超参数 | 建议值 | 原理与踩坑指南 |
|---|---|---|
| 学习率 | **1e-5 ~ 5e-5** | 比预训练低一个数量级。太大→遗忘通用能力，太小→学不动 |
| 学习率调度 | **Cosine decay + warmup** | warmup=总步数 1-3%。从峰值衰减到 1/10 |
| Batch Size | **128-512 条/步** | (全局)取决于 GPU 显存。梯度累积可等效增大 batch |
| 训练量（Token 数） | **领域数据 1-3 个 epoch** | 关键决策，见 4.3 |
| 序列长度 | **4096 或 8192** | 客服对话场景建议 8192（多轮对话上下文长） |
| 优化器 | **AdamW** | β1=0.9, β2=0.95, weight_decay=0.1 |
| Dropout | **0** | 沿用预训练惯例 |
| 梯度裁剪 | **1.0** | 防止 loss spike |

### 4.3 训练量决策：训多久？

**方法：根据 Loss 曲线动态决定，不拍固定步数。**

```
实操步骤：

1. 先跑小规模实验（1/10 数据量），画 Loss 曲线

   Loss
    │
    │ ╲
    │  ╲________
    │          ╲___________  ← Loss 下降速率明显变缓
    │                        ╲________
    └────────────────────────────── Steps
                                ↑
                          这个拐点附近 ≈ 1个epoch

2. 设置验证集（从训练数据中划出 1-2%）
   → 每 500-1000 步算一次 Val Loss
   → Val Loss 不再下降或开始上升 → Early Stop

3. 额外监控：通用能力测试集得分是否开始下降

经验参考：
  - 领域数据 10 亿 token → 通常 1-2 epoch 足够
  - 领域数据 1 亿 token  → 可能需要 2-3 epoch
  - 领域数据 <1000 万 token → 可能 3-5 epoch，但过拟合风险高，考虑数据增强
```

### 4.4 防止灾难性遗忘

**CPT 最大风险：领域能力强了，通用能力崩了。**

| 策略 | 实现方式 | 推荐度 | 说明 |
|---|---|---|---|
| 通用数据混合回放 | 每个 batch 中领域:通用 = 85:15 到 90:10，一起训练 | ★★★★★ 必做 | 最简单有效的防遗忘手段 |
| 低学习率 | LR = 基座预训练 LR 的 1/5 到 1/10 | ★★★★★ 必做 | 减小参数更新幅度，保底措施 |
| EMA | 对模型参数做指数移动平均 | ★★★ 可选 | 有一定泛化提升 |
| LoRA/Adapter | 只训练少量参数，冻结基座 | ★★ 特定场景 | 资源受限时的替代方案，但效果上限低于全参数 CPT |

### 4.5 课程学习（推荐）

**由易到难、由结构化到非结构化，逐步训练，效果通常优于直接全量混合。**

```
阶段1（总步数 ~20%）：结构化知识优先
  ├─ 产品手册、FAQ、政策文档
  ├─ 内容：概念定义、参数表格、流程说明
  └─ 目标：让模型先掌握领域基本词汇和概念框架

阶段2（总步数 ~40%）：半结构化数据
  ├─ 工单数据（有清晰的问题-方案结构）
  ├─ 内容：故障描述→诊断过程→解决方案→结果
  └─ 目标：让模型学会领域的推理链模式

阶段3（总步数 ~40%）：非结构化对话
  ├─ 客服聊天记录、论坛帖子、社交媒体评论
  ├─ 内容：口语化表达、反讽、模糊描述、情绪化语言
  └─ 目标：在掌握领域知识的基础上，适应真实用户的自然语言分布

设计原理：
  如果一开始就给模型看 "我那个phone的screen碎了，你们这quality太差了"
  → 模型连 "phone" 在客服语境下指什么都不知道，学习效率低
  先看产品手册 → 知道华为卖什么手机、屏幕有哪些技术
  再看用户怎么描述屏幕问题 → 学习效率高很多
```

## 五、Phase 3：训练执行与监控

### 5.1 训练环境

| 组件 | 选型建议 |
|---|---|
| 训练框架 | LLaMA-Factory（Qwen/Llama 系列最友好）/ Megatron-LM（大规模分布式）/ DeepSpeed |
| 分布式策略 | 7B：4-8 卡 A100/H800 + ZeRO-2/3<br>70B：多机多卡 + Megatron TP/PP |
| 计算精度 | BF16 训练，FP32 optimizer states（BF16 比 FP16 更稳定，不易溢出） |
| 显存优化 | Gradient Checkpointing + Flash Attention 2 |

### 5.2 训练监控面板

运行期间用 WandB / TensorBoard / MLflow 实时监控：

| 实时监控指标 | 告警阈值 / 异常信号 |
|---|---|
| Training Loss | ↓ 持续下降，出现剧烈震荡→排查 |
| Validation Loss | ↓ 持续下降，连续 N 步不降→可能过拟合，考虑 early stop |
| Learning Rate | 按 schedule 变化，偏离→检查配置 |
| Gradient Norm | 持续 >5→梯度爆炸风险。突然变 0→梯度消失 |
| Token Throughput | 突发下降→硬件/IO 问题 |
| GPU 利用率 | >90% 正常，突发下降→排查 |
| GPU 内存 | 不触发 OOM，预留 5-10% buffer |

### 5.3 Checkpoint 策略

```
保存频率：
  ├─ 每 1000 步：常规 checkpoint（保留最近 5 个，自动淘汰旧的）
  ├─ 每 5000 步：永久 checkpoint（不淘汰，用于回溯对比）
  └─ Val Loss 最佳：标记为 best_checkpoint

保存后自动评测：
  每个 checkpoint 保存后，自动跑一个小型评测集，记录分数
  → 随时知道每个 checkpoint 在各能力维度上的表现
  → 最终用的不是"训到最后那个"，而是"综合表现最好的那个"
```

### 5.4 容错与断点续训

```
关键措施：
  ├─ 训练脚本写入 checkpoint 时才删除旧 checkpoint（防止写一半崩溃导致全丢）
  ├─ 开启 watchdog 进程监控训练进程存活
  ├─ 异常退出后自动从最新 checkpoint 恢复
  └─ 记录每次中断原因供事后分析
```

## 六、Phase 4：评测体系

### 6.1 评测金字塔

```
                    ┌─────────────────────────┐
                    │     CPT 评测金字塔       │
                    │                         │
                    │  L4  业务能力评测（人工）  │  ← 最可信，但最贵
                    │      ↑                  │     关键节点必做
                    │  L3  分维度自动评测       │  ← 核心层
                    │      ↑                  │     每轮CPT必做
                    │  L2  通用能力退化检测      │  ← 安全网
                    │      ↑                  │     每次必做
                    │  L1  训练指标监控          │  ← 必要但不充分
                    └─────────────────────────┘     PPL下降≠能力提升
```

### 6.2 L1：训练指标

参见 5.2 的监控面板。**注意：PPL 下降只代表分布更匹配了，不代表能力提升了。**

### 6.3 L2：通用能力退化检测

**目的：确保 CPT 没有让模型变笨。**

| 评测集 | 测什么 | 推荐基准 |
|---|---|---|
| 综合知识+推理 | 通用知识掌握和推理能力 | MMLU / C-Eval |
| 数学推理 | 数值计算、逻辑推理 | GSM8K / MATH |
| 代码能力 | 程序理解与生成 | HumanEval |
| 中文综合 | 中文语言能力 | CLUE / SuperCLUE |

**判定标准：**

| 下降幅度 | 判定 |
|---|---|
| <3% | 正常波动，无需处理 |
| 3-8% | 需关注，排查原因 |
| >8% | 严重遗忘，需调整策略（降低LR / 增加通用数据 / 减少训练步数） |

### 6.4 L3：分维度自动评测（核心层）

**构建原则：**
1. 评测数据必须和训练数据严格无重叠
2. 覆盖 Easy / Medium / Hard 三个难度层
3. 包含常见 Case（测知识掌握）和罕见 Case（测泛化）
4. 自动化可复现（一模一样的题目，每轮实验都能跑）

**评测维度：**

| 评测维度 | 评测方式 | 数据来源 | 考察什么 |
|---|---|---|---|
| 领域知识准确率 | 选择题 / 填空 | 产品手册抽取 QA，人工验证答案 | "知不知道" |
| 领域术语理解 | 完形填空 / 改写评测 | 领域术语→通用语改写，GPT-4 评分语义一致性 | "理不理解" |
| 故障-方案匹配 | 选择题 + 开放式 | 工单中抽取，人工标注正确方案 | "会不会推理" |
| 非标准表达理解 | 开放式问答 | 社区真实帖子，人工标注正确含义 | "听不听得懂人话" |
| 反讽/情绪识别 | 二分类 / 多分类 | 客服对话片段，人工标注 label | "会不会读空气" |
| 对话续写合理性 | 开放式续写 | 对话片段，GPT-4 + 人工双重评分 | "会不会回应" |

### 6.5 L4：业务能力人工评测

**终极标准。关键节点必做（最终选模型、交付前）。**

```
方案：
  ├─ 邀请 5-10 位资深客服
  ├─ 准备 50-100 个真实业务场景（涵盖各种难度）
  ├─ 盲评：客服不知道哪个回答来自哪个模型
  ├─ 评分维度：
  │   ├─ 知识准确性（1-5分）
  │   ├─ 回答恰当性（1-5分）
  │   ├─ 话术自然度（1-5分）
  │   └─ 是否愿意在真实工作中使用（是/否）
  └─ 统计：Base Model vs CPT Model 对比

成本估算：50 场景 × 2 模型 × 3 客服 = 300 次打分
```

## 七、Phase 5：迭代优化

### 7.1 常见问题排查指南

| 问题现象 | 可能原因 | 解决方向 |
|---|---|---|
| 领域 PPL 下降但能力评测分数没涨 | 数据有噪声/有毒；评测集泄露到训练集 | 检查数据质量；重建评测集 |
| 领域知识涨了但理解能力没涨 | 文档类数据占比太高，对话类不足 | 调整配比，增加对话/社区数据 |
| 理解能力涨了但知识不准确 | 对话太多，结构化知识太少 | 增加产品文档/FAQ 占比 |
| 通用能力大幅退化 | 学习率太高；通用数据太少；训太久 | 降低 LR；增加通用回放；early stop |
| 模型输出变得很"机械" | 模板化数据（系统自动回复）占比太高 | 清洗模板化内容；增加自然对话 |
| 训练 loss 不稳定，频繁震荡 | 学习率太高；数据质量不均；batch 太小 | 降低 LR；排查数据；增大 batch |
| 对长对话理解差 | 序列长度不够；长对话样本少 | 增大 seq_len；专门构造长对话数据 |
| 反讽/情绪理解没涨 | 对话数据不够/质量不高 | 增加高质量真实对话占比 |

## 八、关于涌现能力

**"奇招"（涌现能力）= CPT 创建的领域表征空间 + 基座模型的通用推理能力**

涌现能力无法刻意制造，但可以创造条件让它更容易发生：

1. **数据覆盖面要广**：不能全是"问题 A→答案 A"的工单。必须包含自然对话、闲聊、边界 case、模糊表达。单一分布的数据压缩了涌现空间。
2. **不要过早进入 SFT/RL**：SFT/RL 在 CPT 之上收束。CPT 没做透就急着 SFT = 在没长好的身体上穿紧身衣，限制生长方向。
3. **评测要留"开放题"**：除了选择题，一定要有开放式评测（对话续写、自由问答）。涌现能力在选择题里看不出来，在开放题里会惊艳你。
4. **涌现的判据**：当你发现模型能正确处理一个 CPT 语料里从未出现的客服场景时，涌现就发生了。

## 十、关键认知总结

1. **CPT 不是"把数据丢进去训一下"，而是一个完整的系统工程。** 数据工程、训练策略、评测体系、迭代优化——每一步都有方法论和坑。

2. **数据质量决定天花板。** CPT 花 50% 的精力在数据工程上是值得的。劣质数据训练不出好模型，且数据问题在训练完才发现，返工成本极高。

3. **评测体系是"眼睛"。** 没有评测的 CPT 是在黑暗中开车。评测体系要在训练开始前就建好，不是训完再想怎么测。

4. **CPT 是最大杠杆，但不是全部。** CPT → SFT → RL 是有明确分工的流水线。CPT 做好了，后续 SFT/RL 事半功倍。CPT 没做或敷衍了，SFT/RL 在沙地上建楼。

5. **警惕灾难性遗忘。** 通用数据混合回放 + 低学习率是最简单有效的防遗忘组合，不要省略。

6. **数据说话，不走教条。** 配比、学习率、训练量——初始值来自经验，最优值来自实验。每轮实验都应产出评测报告，用数据指导下一轮迭代。
