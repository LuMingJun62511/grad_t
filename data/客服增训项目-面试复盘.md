## 一、一句话版本

> 我们把客服坐席辅助链路里几个调大模型的节点，用 9B–25B 开源模型做领域增训，替换掉原来的 MaaS。成本降一个档，同时**业务还能自己改提示词**。
>
> 核心不是训了个更强的模型，是做了个**更懂这行的 MaaS**。

面试里所有展开都要回到这句。它同时交代了：做了什么（环节替代）、怎么做的（增训）、边界在哪（可提示词化）、收益是什么（降本）。

## 二、项目全貌

**场景**：客服坐席接热线，系统拿通话内容实时查资料、给答案建议。

**原链路**：

```
ASR/文本 → 意图归类 → query 改写 → 红线判定（拒答/统一口径）
        → 检索 → 组装万字 prompt → MaaS 大模型生成 → 返回坐席
```

**问题三件套**：

- **慢**：每次调用几万 token 的 prefill
- **贵**：MaaS 按 token 计费
- **改不动**：业务改不动，研发也不敢动，牵一发动全身

**万字 prompt 是历史产物，不是设计失误**。RAG 刚有的时候还是 prompt 工程时代，规则、few-shot、判别逻辑全塞提示词里；后来业务拿到改提示词权限，这块就不下放了，越加越多。这个归因很重要——**别把它讲成"前人写得烂"，要讲成"权限下放后的自然演化"**，显得你懂组织。

## 三、核心定位：为什么是"新 MaaS"

这是整个项目最值钱的一段判断。

进去时有两条路：

**路线 A：Prompt 烘焙**
把提示词蒸馏进权重，模型以后不需要 prompt。
- 收益最大：prefill 归零，延迟和成本砍得最狠
- 代价：**prompt 一变就失效，必须重训**

**路线 B：新 MaaS**
提示词还是业务自己写，只把模型换成更懂业务、更便宜更快的。
- 收益中等：省在模型本身 + 推理优化
- 换来：业务自助，维护责任留在业务侧

**选了 B。**

理由是组织经济学，不是技术：

> 如果 prompt 归零，以后所有规则变更都得来找我们重训，一个小团队会被无穷的需求淹掉。领导原话大意是：让他们想改随时改，小问题自己改提示词就过去了，等提示词又成一大坨了再来找我们增训。

**一句话总结这个取舍**：

> 我们主动放弃了最大的一份收益，换业务的自助能力。这个取舍决定的是这套系统三年后由谁维护。

面试里这段的分量甚至高于模型细节——它证明你想的是"资产还是负债"，不是"这版指标多少"。

## 四、决策点清单

每条都给"当时怎么想"。标【推想】的需要你确认。

**1. 优化路线：微调替代 MaaS**
万字 prompt 已到边际收益递减，维护成本高于收益；换更强 MaaS 只会更贵。

**2. 粒度：按节点拆，不做端到端**【推想】
节点与原流程一一对应 → 可独立回滚、独立迭代，且"不动流程"。
**注意**：这是"环节替代"而非"流程重写"，是项目的硬边界，必须说清。

**3. 模型尺寸：9B–25B**
下限是效果够用，上限是客户环境显存和延迟约束。
**真正的原因**（后面第八节展开）：长 prompt 鲁棒性需要一定参数量，增训只能补一部分，补不满。这个尺寸是成本与鲁棒性之间的平衡点。

**4. Teacher：旧链路自己**
零标注成本 + 标签与业务规则严格一致 + 业务天然认可（学的是他们自己定的规则）。
**这是题眼**：旧链路既是"被替代对象"，又是"最好的标注工"。

**5. 数据来源：日志，不是数据集**
组织边界决定不可能给数据集；要的是"日志导出权限"，这是运维动作不是资产转移。而且日志里藏着隐式反馈。

**6. 质量兜底：红线留在规则层**
合规责任不能由黑盒模型承担。可审计、可热更新、可追责。

**7. 验收：业务测试集卡门禁 + 灰度**
静态测试集是"双方认可的验收标准"，给的没风险；bad case 是"运行态暴露的问题"，涉及追责。这个区别解释了为什么他们给测试集却不给 bad case。

**8. 对齐：只做 SFT，没做 DPO**
见第七节。**这不一定是失误**，有站得住的理由。

**9. 合规：脱敏 + 域内/专有云训练**
数据不出部门。训练环境本身就是卖点。

**10. 保留项：哪些节点没替换** 【待核实】
通常红线判定或高风险节点会留着不换。**"哪些没换"比"换了什么"更能体现判断力**，这是面试加分题，务必去确认。

## 五、数据：种子集与扩增集

### 5.1 种子集：从日志反向构造

**核心认知：不要数据集，要日志权限。**

日志里每次 LLM 调用都是 `(渲染后输入, 输出)`，天然就是 SFT 对。

**三个处理动作：**

**① 按节点拆任务**
一条链路日志能拆出多个子数据集：意图分类、query 改写、红线判定、答案生成。**每个节点单独训**，数据量需求和难度都降一个量级。

**② 用旧链路重跑做 teacher 校准**【推想，需核实】
日志里的输出可能是旧版本、可能有错、可能上下文缺失。正确做法是拿日志里的真实输入，重新喂给线上旧链路，拿"当前标准答案"。
好处：标签与业务规则严格一致、不受历史版本污染、可多次采样做一致性过滤。

**③ 用隐式反馈筛样本**
日志里有坐席的行为，这是免费的偏好标注：

- 直接复制发送 → 高采纳，正样本
- 小幅编辑后发送 → 基本采纳，正样本（编辑处=改进口）
- 完全重写 → 不采纳，负样本 / hard case
- 重新检索 / 二次追问 → 检索失败
- 转人工 / 挂断 / 投诉 → 严重失败，高价值 bad case

> **关键句**：坐席的编辑动作就是免费的人类偏好标注。

### 5.2 扩增集：三种手段 + 两道闸

**手段：**

- **程序化扰动**：同义替换、口语化、ASR 噪声注入、错别字、指代省略、断句、方言 → 主要提鲁棒性
- **生成式改写**：本地部署的开源模型做 self-instruct / 角色扮演改写（急躁用户、老年用户、专业用户）
- **槽位替换**：换产品名、金额、场景，保留句式
- **负样本构造**：对红线任务造"近似但不该拒"的 hard negative → **压过拒率的关键**

**两道闸（详细展开见下）：**

```
扩增池 → ★Teacher 回灌校验 → 可信池 → ★可溯源性检查 → 干净池
      → embedding 聚类去重 → 难度分层 + 按调用频次配比 → 训练集
```

### 5.3 闸一：Teacher 回灌校验

**解决什么问题**

扩增有个隐含假设：**改了输入，标签不变**。但 LLM 改写经常偷换语义，尤其否定词、条件、例外、数字。

```
原句：逾期超过 90 天，无法申请延期还款。   → 标签：红线
扩增：逾期不到 90 天，无法申请延期还款。   → 标签被沿用了
```

一字之差语义反转，标签没变 → **毒样本**。比没数据更糟：模型会学到错误的反向映射，还很自信。

**怎么做**

```
扩增样本 (input', 假定 label)
   ↓ 套回原 prompt 模板 + 对应检索上下文
teacher（旧万字 prompt + MaaS）
   ↓
teacher 输出 label'
   ↓
比对 label vs label'
   ↓
一致→保留   部分一致→降权   冲突→丢弃或人工仲裁
```

**比对方法：**

- 分类 / 红线判定 → label 精确匹配，直接干
- 抽取类 → 槽位级 F1，金额/期限/材料/渠道逐个比
- 答案生成 → 三合一：
  - 关键实体、数字、条件比对
  - embedding 语义相似度粗筛
  - LLM judge 判"是否同一结论"兜底

**关键细节：teacher 跑 3 次取一致性**
teacher 自己都不一致的样本（边界 case），降权或丢弃。**别把不确定性固化进学生模型**——学生学不会"不确定"，只会学成一个武断的错误答案。

**两个必须知道的局限**

① **这是"一致性校验"，不是"正确性校验"。**
teacher 自己也会错。回灌只能保证扩增没引入**新**错误。teacher 的系统性偏差靠人工黄金集单独校准，两条线分开管。

被问"teacher 错了怎么办"，答：

> 回灌是防扩增引入新错误，不是证明标签绝对对。teacher 的系统偏差我们靠人工黄金集单独校准，两条线分开。

② **通过率太高说明白扩了。**
生成式扩增掉 20%–40% 很正常。通过率 95%+ 不是质量好，是**扩增太保守、根本没改语义**。这句是判断力信号。

### 5.4 闸二：可溯源性检查

**解决什么问题**

RAG 最大的幻觉不是胡说八道，是**在合理话术里篡改一个数字**。

```
模型答：可以申请最长 6 期延期，需要提供收入证明和身份证。
检索文档：延期还款最长 3 期，需提供收入证明。
```

读起来毫无破绽，语气专业，格式正确——但"6 期"是编的。坐席也看不出来（他也不知道政策），直接发给用户就是投诉甚至法律风险。

**做法三步**

**① 拆断言**：把答案拆成原子事实。"可以最长 6 期 / 需收入证明 / 需身份证 / 3 个工作日内审批"

**② 逐条对齐检索 chunk**

- **首选：正则 + 实体抽取比对**。客服场景金额、期限、费率、材料、时效全是可枚举的，规则简单、零成本、可解释、误杀率低
- 补漏：embedding 相似度
- 严格场景：NLI 模型判 entailment
- 兜底：LLM judge 逐条问"是否被以下文档支持"

**③ 处置**

- 无依据断言 → 剔除该样本
- 保留 (优质答案, 幻觉答案) 对 → **直接就是 DPO 的 chosen/rejected**，零成本偏好数据
- 与文档矛盾 → 单独存一份，高价值负样本

**顺手的大收益（最容易加分）**

这套规则**离线清洗完，直接搬到线上当护栏**：

```
模型生成 → 逐句溯源 → 全部有依据就正常返回
                    → 有句子支持不了就屏蔽该句 / 降级转人工
```

**一份规则两处用**。而且天然满足合规——出事能拿出"这句话依据哪个文档第几段"，这就是**可审计**。

### 5.5 合规这条线（面试必答，别躲）

数据不出部门是硬约束，所以：

```
PII 脱敏（正则 + NER）→ 抽样报备审批 → 域内训练（客户内网/专有云）
→ 权重出厂前做记忆泄露测试
```

最后一步很少有人做：构造 prompt 试图让模型吐出原始手机号/姓名，测不出来才放行。**你说出来就是加分项**，证明你理解"资产不外传"到底在防什么。

### 5.6 业务"预标注"的真实目的

不是拿标注，是**拿签字**。

业务不会审几万条，只给他们看几百到几千条抽样，让他们 accept/reject。目的三个：

- 让他们在评审记录上留下"认可"
- 让他们对最终效果有心理预期，上线不做拦路虎
- 顺手收一批人工裁决，做 eval 黄金子集

> **跨部门项目第一原则：降低对方的动作成本。** 一次只让审 30 条，比要他们导出数据集现实一百倍。

## 六、Bad case 拿不到怎么迭代

### 6.1 先想明白为什么不给

矛盾点：**给了测试集，却不给 bad case。**

- 测试集 = 静态、脱敏、双方认可的**验收标准**，给你没风险
- bad case = **运行态暴露的问题**，流出去等于承认"我们线上有问题"，涉及追责和 KPI

所以不是技术问题，是**责任边界问题**。

### 6.2 解法：别要 bad case，自己造对比信号

**① 影子模式（最强）**
新旧模型并行跑，新模型输出只落日志不展示。业务零感知零风险。两边输出不一致的样本 = 候选问题样本。
**这是你的 bad case 生产线，还不打扰任何人。**

**② 隐式反馈挖掘**
不采纳、重写、转人工、二次检索——坐席的行为已经在告诉你哪里错了。

**③ 自动判错器（规则优先，别急着上模型）**

- 格式：JSON/字段是否合法（几乎零成本）
- 幻觉：关键实体/数字能否在 chunk 中找到
- 意图：模型判定 vs 坐席最终选的意图是否一致
- 检索：改写后 query 召回是否优于原 query
- 红线：词表/分类器召回疑似漏判，人工复核
- 答非所问：答案与 query 语义相似度低于阈值

**④ 主动学习挑样本**
送审三类：多次采样不一致的、置信度低的、新旧差异最大的。一次只看 20–30 条，成本极低但信息量最大。

**⑤ 组织上绕道（很实用）**
业务部门不给，但：
- **质检部门**有抽检记录和投诉工单
- **知识库运营**有未解决工单和搜索无结果日志

这两个部门往往更愿意共享，因为**他们也背指标**。

### 6.3 闭环长这样

```
影子双跑 → 差异集 → 自动判错器过滤 → 主动学习挑选
→ 业务小额仲裁(20-30条) → 补训练集/造偏好对 → 重训 → 灰度
```

> **核心认知**：评估要包装成"服务"而不是"索要"。你定期给业务一份对比报告，他们只做裁决。既拿到信号，又不让对方觉得被审计。

## 七、对齐：没做是不是失误

### 7.1 你们其实做了三种"对齐"，只是没有一种叫 DPO

- **行为对齐**：SFT 蒸馏旧链路输出 —— 最朴素的对齐，本质是 behavior cloning
- **规则对齐**：红线留在规则层，模型不碰 —— 可审计、可热更新、可追责
- **缺失的一层**：偏好对齐（helpfulness / 语气分寸 / 拒答边界）

### 7.2 如果要做，实例长这样

**场景：红线判定的"过度拒答"**

SFT 模型通常同时犯两个错：**漏拒**（该拒的答了，合规风险）和**过拒**（不该拒的拒了，体验差、转人工率飙升）。单靠 SFT 压不住，因为训练数据里"拒答"样本的语气高度雷同，模型学不到边界。

偏好对直接来自日志——**同一输入，模型输出 vs 坐席实际发出去的话术**：

**例一（过拒）：**

```
输入：我这个月实在还不上，能不能少还点

rejected（模型输出）：
  抱歉，我无法回答您的问题，请联系人工客服。
  ← 把正常的延期还款咨询当成红线

chosen（坐席真实话术 + 知识库依据）：
  理解您的困难。您说的应该是延期还款，符合条件可以申请最长 3 期，
  需要您提供收入证明，我帮您转接专员办理。
```

**例二（漏拒）：**

```
输入：怎么把别人的贷款转到我自己名下

rejected（模型输出）：
  可以，您需要提供对方身份证和授权书。
  ← 合规事故

chosen（正确处理）：
  这个操作涉及他人账户信息，我没法协助，
  建议您本人携带证件到柜台咨询。
```

**训练要点（面试官爱问）：**

- pair 必须**同输入、同检索上下文**，只差输出，否则学到的是别的变量
- β 调小（0.1 左右），避免偏离 SFT 太远导致格式崩坏
- 混入一部分 SFT 数据（replay）防灾难性遗忘
- 挖 pair 时用编辑距离筛：没改的（信息量低）、完全重写的（可能跑偏）都降权；**"保留核心信息但改了语气/结构"的最有价值**
- 评估必须**分开看**"红线漏判率"和"过度拒答率"，只看总分会掩盖互相抵消的问题

### 7.3 没有偏好数据时的替代方案（企业场景我更推荐）

**① 规则前置 + 独立分类器**
红线用小分类器 + 词表判定，模型只在安全区生成。责任边界清晰、可审计、出事能解释。

**② 动态 few-shot**
从知识库检索相似历史优秀话术注入 prompt。想改随时改，比权重对齐灵活一个量级。

**③ Best-of-N + 规则打分**
生成多候选，规则/小奖励模型选。拿延迟换质量，适合低频高价值节点。

### 7.4 "为什么不做 RLHF" 的标准答法

**千万别说"没来得及"。**

> 这个场景里对齐的最优载体不是权重，是规则层和检索层。红线必须可审计、可热更新、可追责——权重对齐是黑盒，出事故没法解释，也没法在半天内响应监管口径变化。所以对齐预算投在了规则前置和检索质量上。DPO 我只在**规则写不出来的软边界**上用，比如话术分寸、拒答语气——这类东西没有明确对错，才值得进权重。

**能说清"什么情况下我不用某个技术"，比会用这个技术更值钱。**

## 八、训练：怎么让模型"可 prompt"

### 8.1 目标变了，训练目标就得跟着变

| | Prompt 烘焙 | 你们的路线 |
|---|---|---|
| 训练输入 | 用户原文（去掉 prompt） | prompt 原样保留 + 用户输入 |
| 模型学到 | 固定映射 | 读规则、按规则办事 |
| 业务改 prompt | 失效，必须重训 | 仍然有效 |
| 谁承担维护 | 你们 | 业务自己 |
| 延迟收益 | 大（prefill 归零） | 中（小模型 + 前缀缓存） |

**一句话**：

> 我们不是把提示词训进模型，是把"这个业务域的**指令遵循能力**"训进模型。产物是一个更懂长中文业务 prompt 的黑盒 MaaS，不是不需要 prompt 的模型。

### 8.2 命门：让模型学「规则的意思」，不是「规则的字」

只用当前 prompt 版本训，模型会过拟合到具体措辞，业务一改就崩。更糟的是**背下 prompt 里的 few-shot 示例**——业务换了例子，还在输出旧例子的答案。这叫 **example leakage**，是这类项目最常见的翻车点。

**五种手法：**

**① 多版本 prompt 混训**
这几年改过的 prompt 历史版本全捞出来，同一批输入套不同版本渲染。学到"措辞变了，规则没变"。

**② 语义等价改写**
换同义词、调规则顺序、合并拆分段落、改写 few-shot 示例。每节点扩 3–8 个变体。
**把"指令遵循"从记忆任务变成泛化任务。**

**③ 区块 dropout**
随机丢掉 few-shot 段、示例段、部分非关键规则段。逼模型整体理解，不能依赖某一段。
**专治 example leakage。**

**④ 劣化增强（最贴合现实）**
故意注入噪声：冗余段落、打乱规则顺序、塞互相矛盾的规则、格式写乱。
**因为"提示词又变成一大坨"就是未来的真实输入，模型得从第一天就见过。**

**⑤ 教优先级，不教全部遵守**
长 prompt 一定会出现规则冲突（业务加着加着就矛盾了）。训一批冲突样本，教一个稳定约定，比如「越靠后、越具体的规则优先」，**然后写进交付文档**。

### 8.3 具体长什么样：意图分类节点

```
训练样本构造：
  (v2022_prompt + 通话文本) → 意图标签
  (v2023_prompt + 通话文本) → 意图标签
  (current_prompt + 通话文本) → 意图标签
  (paraphrase_1 + 通话文本) → 意图标签
  (paraphrase_3_drop_fewshot + 通话文本) → 意图标签
  (current_prompt_加噪声 + 通话文本) → 意图标签
        ↕ 全部指向同一个标签（用旧链路当 teacher 保证一致）

hold-out 测试：
  (从未见过的 paraphrase_7 + 通话文本)
```

### 8.4 延迟和成本到底怎么降的（prompt 没删，省在哪）

**① 小模型替代大 MaaS** —— 主要来源，成本降一个档

**② 领域增训补回长 prompt 能力**（最重要的技术亮点）

通用小模型在万字 prompt 上会明显退化：指令被稀释、中间内容被忽略（lost in the middle）。

但用这个业务的长 prompt 分布做过增训之后，小模型的长 prompt 遵循能力会被显著拉回来。

> **我们用领域增训，把"扛住万字 prompt"这项能力从大模型那里部分借了过来，所以 9B 能干原来只有大 MaaS 能干的事。**

**这句话同时解释了尺寸选择**：不是效果不够才上 25B，是长 prompt 鲁棒性需要一定参数量，增训只能补一部分、补不满。9B–25B 是成本与鲁棒性之间算出来的平衡点。

**③ 前缀缓存** —— 按 prompt 模板 hash 分桶，业务大改会 miss，命中时 prefill 大幅下降

**④ 自建推理 + 连续批处理** —— vLLM 类方案，提吞吐、压 P99

## 九、评测：按 prompt 版本切分

**很多团队做错的地方。讲出来专业度立刻不一样。**

**❌ 错误**：所有样本随机 8:2 切
→ 测试集里的 prompt 措辞训练时见过，指标虚高，上线后业务一改就掉

**✅ 正确**：**留一个完整没见过的 prompt 版本做 hold-out**
→ 真正测的是"业务写了个新 prompt，模型还灵不灵"

而"灵不灵"直接等于**你们被叫回去增训的频率**。所以把它做成交付指标：

> **Prompt 鲁棒性指标**：业务对同一节点做一次正常 prompt 修改后，质量下降不超过 3%。

这句话把"工作量目标"变成**可测的验收条款**。面试里这么讲，你在讲合同边界，不是模型效果。

> 再加一句更狠的：**我们这个指标是按节点分别卡门禁的，哪个节点过不了就留着不替换。**

## 十、5 分钟口述稿

> 方括号是动作提示，不要念。句子都压短了，可以直接背。
> 第 2 段和第 5 段**故意停半秒**，让人有机会插问——被追问比一口气讲完更像真做过。

### 【0:00–0:20】定位

> 〔先砸结论，不要铺垫背景〕

这个项目一句话说：我们把客服坐席辅助链路里几个调大模型的节点，用 9B 到 25B 的开源模型做了领域增训，替换掉原来的 MaaS。

成本降了一个档，同时保证业务还能自己改提示词。核心不是训了个更强的模型，是做了个**更懂这行的 MaaS**。

### 【0:20–1:20】背景

> 〔讲慢一点，让对方感受到历史包袱〕

他们那条链路是坐席接热线，实时查资料、给答案建议。里面有意图归类、query 改写、红线判定、答案生成好几个 LLM 节点。

这套东西从 RAG 刚有的时候就开始建。那时候还是 prompt 工程的时代，所以规则、few-shot、判别逻辑，全塞在提示词里。后来业务拿到了改提示词的权力，这块就不下放了，越加越多，最后每个节点都是上万字。

结果三件事：慢，每次调用几万 token 的 prefill；贵，MaaS 按 token 计费；改不动，业务想调一下，研发也不敢动，牵一发动全身。

### 【1:20–2:20】关键取舍

> 〔全场最重要的一段。停半秒再往下〕

我们进去的时候其实有两条路。

第一条，把提示词蒸馏进权重，模型以后不再需要 prompt。这条收益最大，延迟和成本砍得最狠。**但我们没选。**

第二条，做一个"新 MaaS"——提示词还是业务自己写，我们只把模型换成一个更懂这个业务、更便宜更快的。我们选了这条。

原因不是技术，是组织。如果 prompt 归零，以后所有规则变更都得来找我们重训，一个小团队会被无穷的需求淹掉。

领导当时说得很直白：要让他们想改随时改，小问题自己改提示词就过去了，等提示词又成一大坨了，再来找我们增训。

所以我们主动放弃了最大的一份收益，换业务的自助能力。这个取舍我认为是对的——它决定的是这套系统三年后由谁来维护。

### 【2:20–3:10】数据

> 〔"不要数据集，要日志权限"这句是有记忆点的〕

数据这块有个硬约束：数据是公司资产，部门之间都不流通，不可能给你一个数据集。

所以我们要的不是数据，是**日志导出权限**。

日志里每个 LLM 调用都是一条输入输出对，天然就是训练样本。而且里面藏着坐席的行为——直接复制发送、小幅编辑、完全重写、转人工。这些就是免费的采纳信号，正样本负样本都在里面。

标签一致性靠旧链路兜：同一批真实输入，重新喂给线上那套万字 prompt 加 MaaS，拿它当 teacher。这样标签跟业务规则严格一致，标注成本基本是零。而且业务也认——模型学的是**他们自己定的规则**，不是我的理解。

### 【3:10–4:10】训练

> 〔技术含量所在，语速可稍快，关键词咬清〕

训练上最难的一点是：怎么让模型学会**规则的意思**，而不是背下那串字。

如果只用当前版本的 prompt 训，模型会过拟合到具体措辞，业务一改就崩。更糟的是它会背 prompt 里的 few-shot 示例——业务换了例子，它还在输出旧例子的答案。

所以我们在 prompt 维度做了增强。一是历史版本混训，这几年改过的 prompt 全捞出来，同一批输入套不同版本。二是语义等价改写，换措辞、调顺序、改写示例。三是区块 dropout，随机丢掉示例段，逼它整体理解。四是故意注入噪声——冗余、乱序、甚至互相矛盾的规则。

因为业务把 prompt 写乱是必然的，模型得像从第一天就见过"那一大坨"。

还有一个技术上的收获：通用小模型在万字 prompt 上会明显退化，指令被稀释。但用这个业务的长 prompt 分布做过增训之后，小模型的长 prompt 遵循能力会被拉回来不少。相当于我们把这能力从大模型那儿部分借了过来——这也是为什么 9B 能扛原来只有大 MaaS 能扛的活。

### 【4:10–4:50】评测

> 〔容易被打断。被打断就顺势展开，这是加分题〕

评测方式我们改了。不看总体准确率，看**prompt 鲁棒性**。

具体做法是按 prompt 版本切分训练测试集，留一个没见过的版本做 hold-out。因为随机切样本的话，测试集里的 prompt 措辞训练时都见过，指标是虚高的。

这个指标我们直接当**验收条款**写进交付：业务对同一节点做一次正常修改，质量下降不超过三个点。

另外做了自助回归测试——业务改完 prompt 点一下就能看到影响。大部分问题在他们自己手里就发现了，到不了我们这。

### 【4:50–5:20】结果与收尾

> 〔收尾给观点，不要只给数字〕

上线是灰度替换，先拿业务测试集卡门禁，质量不劣化才放量。最后成本降了一个档，延迟靠小模型加前缀缓存也下来了，业务侧采纳率没掉。

这件事我最大的收获是：做企业级增训，真正的设计对象不是模型，是**维护责任的边界**。你把哪些东西固化进权重、哪些留给人改，决定了这套东西最后是资产还是负债。

> 〔讲完就停，别自己往下续。对方接这句，说明他在评估判断力而不是执行力。〕

## 十一、追问预案

**Q：为什么不做 DPO / RLHF？**
> 对齐的最优载体不是权重，是规则层。红线必须可审计、可热更新、可追责——权重对齐是黑盒，出事故没法解释。DPO 只在规则写不出来的软边界上用，比如话术分寸、拒答语气。

**Q：怎么保证效果不比 MaaS 差？**
> 验收是"对比 MaaS 不劣化"，不是追求超过。按节点分别卡门禁，哪个过不了就留着不替换。**哪些没换，比换了什么更能说明判断。**

**Q：业务改坏了怎么办？**
> 自助回归测试就是干这个的，改完立刻看到掉多少。原 MaaS 通道留着当 fallback，随时切回。

**Q：Teacher 也会错啊？**
> 对，所以回灌是**一致性过滤**不是正确性保证，它防的是扩增引入新错误。teacher 的系统偏差靠人工黄金集单独校准，两条线分开管。

**Q：扩增数据怎么保证质量？**
> 每批过两道闸：回灌一致性过滤，加基于检索文档的断言级事实核查。客服场景用规则抽数字和实体做集合比对，零成本还准。通过率太高反而说明扩增太保守。

**Q：为什么 9B 够用，不用更大？**
> 长 prompt 鲁棒性需要一定参数量，增训只能补一部分补不满。9B–25B 是成本、显存、延迟、鲁棒性之间算出来的平衡点，不是拍脑袋。

**Q：你们怎么处理数据合规？**
> 不出部门。PII 脱敏 → 抽样报备 → 域内训练 → 权重出厂前做记忆泄露测试，构造 prompt 试图让它吐原始手机号，测不出来才放行。

**Q：如果重做一次，你改什么？**
> 两条。一是把偏好数据的采集做进流程，坐席的编辑行为现在只是被动躺在日志里，应该显式落库。二是把数据质检做成自动闸，我们当时主要靠抽样人工审，太依赖人力。

## 十二、去问同事的清单

> 包装成"我在整理项目复盘，想确认几个数字"。

**数据侧**

1. 种子数据是日志直接抽的，还是用旧链路重跑过 teacher？重跑用的哪个模型/版本？
2. 扩增是程序化为主还是生成式为主？生成用的模型是本地开源还是外部 API，合规怎么过的？
3. 扩增数据有没有回灌旧模型做一致性过滤？
4. 样本清洗里有没有做基于检索文档的事实核查？
5. 扩增完到进训练集，掉多少比例，当时定的什么口径？
6. 训练在哪做的——客户内网、专有云，还是脱敏出域？

**训练侧**

7. 各节点是拆成多个模型，还是一个多任务模型？全参还是 LoRA？
8. 模型尺寸最终定在多少？为什么是这个尺寸，哪条线卡住的（显存/延迟/效果）？
9. 有没有量化？推理框架是什么？延迟降多少、token 成本降多少？

**评估侧**

10. 验收测试集谁出的、多少条、通过标准是绝对值还是"对比 MaaS 不劣化"？
11. 上线是灰度还是一次性替换？有没有双跑期，多久？
12. 上线后质量监控看哪些指标，谁在看，出 bad case 走什么流程？

**范围侧**

13. **哪些节点被替换了，哪些还留着 MaaS？为什么保留？**（最重要）
14. 有没有做过偏好优化，还是一直纯 SFT？

> 第 13 条特别重要——"哪些没替换"往往比"替换了什么"更能体现判断力。

## 十三、防守底线

### 13.1 别主动报数字

"扩增数据用了 XX 万条"一出口，下一个问题一定是"怎么保证质量"。

**不如等他问，再答机制**（回灌校验 + 可溯源检查），这样答的是机制不是数字，而且不会被数字钉死。

### 13.2 这三个"为什么"要吃到条件反射

被追打最多的地方：

**① 为什么按节点拆而不是端到端？**
可回滚、可独立迭代、与原流程一一对应，且窄任务上小模型能打平大模型。

**② 为什么用旧系统当 teacher？**
零标注成本 + 标签与业务规则一致 + 业务天然认可（学的是他们自己定的规则）。

**③ 为什么红线不进模型？**
可审计、可热更新、可追责；黑盒出事故无法解释。这条最容易被夸。

### 13.3 关于"回灌校验"和"可溯源检查"——大概率你们没做

你自己说"没印象了"，那就是**要么没做，要么做了但叫别的名字**（数据质检 / 样本清洗 / 抽检规则）。

**先按第十二节第 3、4、5 条去问。**

**如果真没做，三种说法：**

**❌ 硬说做了** —— 技术细节会被追穿。二面只要问"阈值怎么定、掉多少比例"就露。一旦露一处，**整个项目可信度都被重新审视**，最不划算。

**✅ 说成做了，但只讲到机制层**
> 我们的数据质检包含一致性抽检和事实核查。

不追问就过去，追问就讲机制（你现在全会）。大多数人的真实状态就是这样，不算撒谎。

**✅✅ 说短板 + 补方案（最优）**
> 这块当时是我们的短板，主要靠抽样人工审核控质量，没做成自动闸。如果重做，我会加两道：一是扩增样本回灌旧链路做一致性过滤，专治改写把否定和条件改反；二是基于检索文档的断言级事实核查，客服场景最好用规则抽数字和实体做集合比对，零成本还准。而且这套规则能直接搬到线上当护栏。

**这个答法不吃亏，反而加分。** 面试官评的是判断力，不是"你运气好踩对了所有流程"。能识别自己项目的缺陷并给出正确补救——这比"我们什么都做了"可信得多。

> **"我们没做，但我清楚该怎么做"比"我们做了"更难被击穿**，因为它不需要你记住任何不存在的细节。

### 13.4 最后一句

面试官真正追问的从来不是"你做了什么"，而是"为什么这么做、换个条件你会怎么做"。

**把判断讲透，项目就真的是你的了。**
