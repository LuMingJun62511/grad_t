## 1. 前置：一个 token 在模型里怎么走

**1.1** 输入是一串 token（比如 `A B C D 1 2 3`）。

**1.2** 每个 token 先变成两样东西：
- 一个**向量**（表示"它是什么词"）
- 一个**位置信息**（表示"它排第几"）

**1.3** "向量 + 位置"合起来，就是某个位置上的**输入 X**。

**1.4** 在每一层里，X 各乘一个不同的权重矩阵，得到三个东西：
- **Q**（Query，提问）
- **K**（Key，索引）
- **V**（Value，内容）

**1.5** 然后**注意力**：用 Q 去和所有 K 比对，决定"该看谁"，再按这个权重把 V 汇总起来。

**1.6** 注意力结果 → 加残差 → 进 **MLP**（前馈网络）→ 再加残差 → 进入下一层。

**1.7** 模型有 N 层，1.4–1.6 这个过程重复 N 遍。

> ✅ **这一段如果都懂，就可以往下。**

---

## 2. 缓存的是谁：K 和 V，不含 Q

**2.1** 缓存里存的是 **K 和 V**，**不存 Q**。

**2.2** 为什么不存 Q：Q 是"当前这一步才需要"的东西，算完就用掉了，**不需要留给未来**。

**2.3** 为什么要存 K 和 V：**未来的每一个新 token，都要回头去看前面所有 token 的 K 和 V**，所以必须留着。

**2.4** 一句话：**Q 是提问者，用完即走；K/V 是被提问的对象，要一直留着。**

**2.5** 于是缓存的内容可以写成：

```
第 l 层，第 i 个位置 → (K, V)
```

**2.6** 一个 N 层模型，`ABCD` 这四个 token 占的缓存就是：
**N 层 × 4 个位置 × 2 个向量（K 和 V）**。

---

## 3. 缓存的粒度：按「位置」存，不是按「前缀」存

**3.1** 常见误解：以为缓存里存了 `A`、`AB`、`ABC`、`ABCD` 四份。

**3.2** 实际上**只存了 4 个位置**：

```
位置0 → (K_A, V_A)
位置1 → (K_B, V_B)
位置2 → (K_C, V_C)
位置3 → (K_D, V_D)
```

**3.3** `AB` 不是一份独立缓存，它只是"读前 2 个位置"。

**3.4** `ABC` 同理，只是"读前 3 个位置"。

**3.5** 所以：**前缀不是额外的条目，而是同一串缓存的前几段。**
有了这 4 个位置，就自动"拥有"了 A / AB / ABC / ABCD 整条阶梯。

---

## 4. 为什么必须是「前缀」（最关键的一节）

**4.1** 先给结论：**能复用的只有"从第一个 token 开始、连续相同"的那一段。**

**4.2** 为什么？先看**只有一层**的情况。

**4.3** 第 1 层的输入 X，只由"这个词 + 它的位置"决定。

**4.4** 所以在第 1 层，K 和 V **只跟本 token 和位置有关**，跟别的 token 无关。

**4.5** 也就是说：**如果只有一层，"ABCD 不是前缀"其实也能复用**（只要位置对得上）。

**4.6** 但真实模型有很多层。再看**第 2 层**：

**4.7** 第 2 层的输入 = 第 1 层在位置 i 的**输出**。

**4.8** 而第 1 层的输出，**经过了注意力**——它在位置 i，已经看过前面 0..i 的所有 token 了。

**4.9** 所以第 2 层的 K/V，**依赖整个前缀 0..i**。

**4.10** 小结这条链：

```
层越深 → 那个位置"看过的东西"越多 → K/V 越依赖整个前缀
```

**4.11** 因此，可复用的单位 = **最长公共前缀**。

**4.12** 换句话说：**"必须往前放"不是约定，是多层堆叠逼出来的数学后果。**

**4.13** 反例（务必记住）：

```
❌ 中间相同、前面不同 → 不能复用
   请求C: [C 的头][ 共同段 ][C 的尾]
   请求D: [D 的头][ 共同段 ][D 的尾]
   → "共同段"的上文不同 → 算出来的 K/V 不同
```

## 5. 怎么找命中：vLLM 的「块哈希链」

**5.1** 先引入一个概念：**块（block）**。vLLM 把 token 按**每 16 个一组**切成块。

**5.2** 为了看清过程，本节**假装块大小 = 2**（真机是 16）。

**5.3** 两个请求：

```
请求1: A B C D 1 2 3   → 块: [AB] [CD] [12] [3]
请求2: A B C D 4 5 6   → 块: [AB] [CD] [45] [6]
```

**5.4** 核心规则：**每个块的哈希 = H（本块的 token，前一块的哈希）**。

**5.5** 这叫"链式"——哈希里**包含了它前面所有 token 的信息**：

```
h₁ = H([AB])
h₂ = H([CD], h₁)     ← 里面含 AB
h₃ = H([12], h₂)     ← 里面含 AB、CD
```

**5.6** 这个设计的好处：**前面任何一个 token 变了，它后面所有哈希都变**，旧缓存于是自动失效——不需要额外判断。

**5.7** 请求 1 来了（第一次）：
- 算出 h₁、h₂、h₃ → 哈希表里都没有 → **全部未命中**
- 正常算完，把 h₁/h₂/h₃ 对应的块**留在缓存里**

**5.8** 请求 2 来了：
- 先算出自己的块哈希：h₁、h₂、h₃′（h₃′ 和 h₃ 不同，因为那块的 token 是 `[45]`）
- 从第一个块开始**逐个查表**：
  - h₁ → 表里有 ✅ 命中
  - h₂ → 表里有 ✅ 命中
  - h₃′ → 表里没有 ❌ → **停下**
- **最长命中前缀 = 前 2 个块 = `ABCD`**
- 把这 2 块直接接上（复用，零重算）
- **只对 `456` 做 prefill**

**5.9** 一句话：**命中不是"模糊地找像哪个缓存"，而是"顺着前缀链往前走，走到第一个查不到的地方为止"。**

## 6. SGLang 的做法：radix 树（对照理解）

**6.1** 同一个目标，另一种数据结构：**radix 树**（一种"把公共前缀压在一起"的树）。

**6.2** 你的例子在树里长这样：

```
        (根)
         │ AB
         ●
         │ CD
         ●────────┐
         │12      │45
         ●        ●
```

**6.3** 请求 2 顺着树走 `AB → CD`，再想走 `45` 时发现没有 → 就在那里**长出新分支**。

**6.4** **命中 = 能沿着树走多远。**

## 7. 三个很实际的推论

**7.1 块大小 16 是有代价的**：`ABCD123` 只有 7 个 token = **0 个完整块** → 真实 vLLM 下**什么都缓存不了**。

**7.2 改一个早期 token = 后面全部失效**：因为哈希是链式的。所以"开头放时间戳"不是浪费 1 个 token，而是**废掉整条链**。

**7.3 命中是"精确前缀"**：token 级一字不差，不是"差不多"。这是它和"语义缓存"的根本区别。
